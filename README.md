# Online Voting Polling System

**PollRoom** is a full-stack classroom polling application. Registered, confirmed users create questions with 2–6 choices, vote once per poll, and see final results after voting closes. It solves the practical problem of collecting consistent class or club preferences without manually counting responses.

## Objectives and intended users

Students learn browser forms, `fetch()`, REST endpoints, Express middleware, authentication, relational constraints, transactional operations, and Git. Use this for workshop dates, club activities, class preferences, and similar informal decisions.

Every confirmed account can be a **voter** and a **poll creator**. Creator permissions belong to a particular poll, rather than to a global administrator role. The creator can vote too. No account can edit another person's poll or vote for them through the API.

## Implemented features

- Registration through Supabase Auth and email/password sign-in.
- Authenticated poll directory with title search, open/closed filters, ownership filter, and pagination (12 per page).
- Create a poll with an optional description and a closing time 1 minute–30 days away.
- Publish immediately; questions and choices become immutable.
- One permanent vote per account per poll, enforced by a database primary key.
- Creator-only early closure; scheduled closure is enforced using the database clock.
- Results hidden until closure, including from creators. Closed polls show totals, percentages, top choices, and ties.
- Creator-only deletion of polls that have no votes. Polls with votes are retained.
- Responsive interface, accessible labels, confirmation dialogs, loading/empty/error states, and safe text rendering.
- Health endpoint, request limits, security headers, validation tests, HTTP smoke tests, and safe error responses.

No seeded users or votes are supplied. All demonstration votes should be entered using your own test accounts.

## Technology and architecture

HTML5, CSS3, Vanilla JavaScript → same-origin HTTP requests → Node.js/Express → Supabase Auth and Supabase PostgreSQL.

The browser does not import a Supabase SDK or receive any Supabase API key. The Express server serves `frontend/` and uses `@supabase/supabase-js` to call Auth and the PostgreSQL Data API. The database stores persistent records; browser memory stores only the current login token and UI state.

Necessary packages:

| Package | Purpose |
| --- | --- |
| express | HTTP routes, JSON parsing, static files |
| @supabase/supabase-js | Supabase authentication and database calls |
| dotenv | Load local environment configuration |
| helmet | Security headers, including Content Security Policy |
| express-rate-limit | Limit request and login abuse |

The dependency versions are pinned in `backend/package.json`; the generated `package-lock.json` is included. There is no frontend build step and no external API, image, font, or paid integration required for the core app.

## Step 3: Initialize PostgreSQL

1. In VS Code open `database/schema.sql` and copy the entire file.
2. In the Supabase project open **SQL Editor → New query**.
3. Paste the SQL and click **Run**. Expected result: successful completion without an error.
4. Open **Table Editor** and verify `polls`, `poll_options`, and `votes` exist in `public`.
5. In SQL Editor run:

```sql
select table_name from information_schema.tables
where table_schema = 'public'
and table_name in ('polls', 'poll_options', 'votes');

select relname, relrowsecurity
from pg_class
where oid in ('public.polls'::regclass,
              'public.poll_options'::regclass,
              'public.votes'::regclass);
```

Expected: three table names and `relrowsecurity = true` for all three. Inspect functions under Database functions or query `pg_proc` if needed. The initialization SQL creates five RPC functions and explicitly grants access only to `service_role`.

Run initialization **once in a new project**. It is deliberately non-destructive and will report existing objects if run again. Do not drop populated tables to fix a setup error. Read the error and use a new test project if you need a fresh demonstration database.

### Database design

| Table | Important columns | Rules |
| --- | --- | --- |
| auth.users | id, email, managed authentication fields | Supabase manages identities and password hashing |
| polls | id, creator_id, title, description, ends_at, closed_at, created_at | Creator references Auth user; question length and timestamps constrained |
| poll_options | id, poll_id, label, position | Unique normalized labels and positions per poll; 2–6 options created atomically |
| votes | poll_id, voter_id, option_id, created_at | Composite primary key gives one vote per account per poll; composite foreign key prevents using another poll's option |

A user creates many polls. A poll has multiple choices and many votes. A vote belongs to one user, one poll, and a choice within that same poll. Auth user deletion is restricted when application records reference the user, preserving historical integrity.

`create_poll` creates a question and choices together; any failure rolls the operation back. `cast_vote` and `manage_poll` lock the same poll row. The close-time check uses `clock_timestamp()` after the vote obtains its lock. Duplicate requests cannot insert two ballots for one user. A close/delete request cannot invalidate a simultaneous accepted vote. `list_polls` performs search and pagination. `poll_detail` returns counts only after closure.

No generic `updated_at` trigger is necessary: poll text and choices are immutable; `closed_at` records the only supported poll modification.

## Authentication, ownership, and security

The backend signs in through Supabase Auth and returns only the short-lived access token, its expiry, and the user's ID/email. It discards the refresh token. The frontend keeps the access token in JavaScript memory, never localStorage. Reloading the page or closing the tab requires signing in again. The UI also expires the session at the returned expiry time.

Every private API request sends `Authorization: Bearer TOKEN`. The backend calls `auth.getUser(TOKEN)` to verify the identity with Supabase. It does not trust the browser's submitted user ID, creator flag, or role. RPC actor IDs come only from the verified Auth user. Owner checks execute inside the transactional management function.

Log out clears the current tab's token and UI. **It does not revoke a copied access token**, which remains usable until it expires. This limitation is explicit; do not use this session design for high-stakes elections. Other tabs keep their own memory sessions. Configure sensible Auth token expiry in your project.

RLS is enabled, but there are deliberately **no anon/authenticated table policies**. Those roles also lack table privileges and RPC execution grants. Therefore direct Data API access from a browser token is denied. Express uses a secret key mapping to `service_role`, which bypasses RLS, so the backend's authentication, actor derivation, and database function checks are mandatory. All RPCs use SECURITY INVOKER, a fixed empty search path, and explicit execution grants. They are not public administrative shortcuts.

Security headers restrict scripts, styles, and connections to this app. User text is rendered using `textContent`, not injected HTML. Requests are size-limited and validated server-side; SQL constraints add another integrity boundary. Error responses exclude raw database messages, stack traces, and credentials. Authentication routes are rate-limited. Because authentication uses an explicitly supplied bearer header rather than automatically attached cookies, cookie-based CSRF protection is not needed for this design. CORS is not enabled. Use HTTPS when hosting publicly.

The default rate-limit stores and login sessions are designed for one Node process. Do not blindly enable Express `trust proxy`; configure it for the exact reverse-proxy topology before hosted deployment. Many students behind the same public IP share IP-based request and login limits.

## REST API reference

All successes return JSON. Errors have the form `{"error":"Friendly message"}`. `401` means authentication is missing, expired, invalid, or unconfirmed. Other relevant responses: `400` invalid input, `403` not owner, `404` missing poll/route, `409` duplicate vote or forbidden poll-state transition, `413` body too large, `415` wrong content type, `429` rate limit, and `503` database unavailable. Unexpected internal failures use `500`. Writes require `Content-Type: application/json`, even when no fields are needed.

| Method and path | Body/query | Permission | Success |
| --- | --- | --- | --- |
| GET /api/health | None | Public | 200 `{status:"ok",database:true}` or 503 unavailable |
| POST /api/auth/register | `{email,password}` | Public, rate-limited | 202 `{message}`; account confirmation still required |
| POST /api/auth/login | `{email,password}` | Public, rate-limited | 200 `{token,expires_at,user:{id,email}}` |
| GET /api/polls | `search`, `status=all/open/closed`, `mine=true/false`, `page` | Confirmed user | 200 `{items,total,page,page_size}` |
| POST /api/polls | `{title,description,options:[...],ends_at:ISO8601}` | Confirmed user; becomes creator | 201 `{id}` |
| GET /api/polls/:id | UUID path parameter | Confirmed user | 200 poll detail object |
| POST /api/polls/:id/votes | `{option_id:UUID}` | Confirmed user; open poll; not already voted | 201 `{message}` |
| PATCH /api/polls/:id/close | `{}` | Creator only | 200 `{message}`; repeat close is harmless |
| DELETE /api/polls/:id | `{}` | Creator only; zero votes | 200 `{message}` |

List items contain `id`, `title`, `description`, `ends_at`, `created_at`, `closed`, `is_owner`, and `has_voted`. Poll detail contains `id`, `title`, `description`, `ends_at`, `closed`, `is_owner`, `has_voted`, `can_delete`, `total_votes`, and `options:[{id,label,votes}]`. `total_votes` and every option's `votes` are `null` before closure. Raw ballots, voter emails, and other users' IDs are never returned by poll endpoints. Dates are stored as `timestamptz`, transmitted as ISO timestamps, and displayed in the browser's local timezone.

## Sample classroom workflow

1. Create confirmed demo users A and B. Sign in as A.
2. Create the question **Which workshop should our club host?** with choices **Blender basics**, **Web development**, and **Unity introduction**. Set tomorrow's closing time.
3. Open the poll and cast one vote as A. Results remain hidden.
4. Sign out. Sign in as B in a separate browser profile/private window and vote for a choice.
5. Refresh the poll. B can vote but cannot close or delete A's poll.
6. Return to A and choose Close voting → Confirm. Refresh B's view.
7. Verify the totals and percentages match the two votes. The voted poll cannot be deleted.
8. Create another empty demo poll and delete it to demonstrate the allowed destructive workflow.

## Automated checks and actual verification

From `backend/`:

```bat
npm run check
npm test
```

`check` parses all application JavaScript. `test` uses Node's built-in test runner: eight validation tests plus an HTTP test covering static files, CSP, blocked secret paths, missing authentication, unknown routes, malformed JSON, empty request bodies, and unsupported content types. Tests use inert environment values and never contact a hosted Supabase project. Expected: all 9 tests pass, 0 fail. Tests run in isolated test processes, so their environment overrides do not change your `.env` file.

During generation, the JavaScript syntax checks and included automated tests were executed. Separately, 15 schema/function/privilege checks passed against a local PostgreSQL engine with minimal stand-in Auth tables/roles. These covered creation rollback, duplicate ballots, ownership, closed/expired polls, composite foreign keys, hidden results, and revoked direct access. This local harness is a development verification tool, not an app dependency and not a hosted Supabase test. Actual parallel-client locking behavior still needs the manual concurrency test against your configured project.

Hosted Supabase connectivity, real confirmation emails, and live Auth/database integration were **not tested** because no project credentials were supplied. Run the manual tests after configuration. Rendered browser checks could not run because the available Chromium process failed during graphics initialization in this environment. The interface was not visually verified; run the responsive and keyboard tests above locally.

## Limitations and future improvements

This is informal polling, **not a public election system**. One account is not proof of one real person: someone can create multiple accounts. Polls are visible to all confirmed registered accounts. There is no invitation list, official voter roll, ballot anonymity/cryptography, independent audit trail, scheduled opening, global administrator, edit/reopen workflow, password-reset UI, refresh-token session renewal, vote changes, or live results streaming. Anyone with database administration access can inspect or alter stored ballots; creators cannot see raw ballots through the app.

Logout is local to a tab and cannot invalidate a stolen token immediately. The default rate limiter is in memory. This version does not include deployment configuration, load testing, multi-instance rate limits, institution identity verification, or automated tests against hosted Supabase. Free service limits and account settings may restrict large classroom demos.

Possible next steps are institution-approved identity verification and eligible voter lists, audited server-side sessions, password recovery, accessibility review, exports of aggregate results, deployment with HTTPS and a correctly configured proxy, and stronger operational monitoring. Keep these separate from the beginner MVP.
